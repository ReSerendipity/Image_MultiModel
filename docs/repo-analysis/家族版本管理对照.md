## 2. 按载体风险的横向对比（重点：哪些容易漏）

| 风险维度      |  DraftPeek | Image |          MiniMax          |        SeedVR2        |           TTS          | SpiritPal |
| --------- | :--------: | :---: | :-----------------------: | :-------------------: | :--------------------: | :-------: |
| 载体数       |    1（集中）   |   1   |             2             |           1           |            2           |     3     |
| 需人工同步处    | 0（task 自动） |   1   |             2             |           1           |            2           |     3     |
| 有自动门禁?    |   无(低风险)   |   无   |             无             |           ✅           |           ⚠️           |     ✅     |
| **发版易漏点** |     几乎无    |   无   | 后端版本号与 package.json 可能不同步 | 改完需跑 test\_version.py | **只改一次易漏 config.yaml** | 漏一处即 CI 拒 |

> **结论**：最需要小心的两处
>
> 1. **TTS\_MultiModel**：release-please 只动 `pyproject.toml`，`config.yaml` 的 `version` 不会自动跟随（前端缓存参数 `?v=app_version` 依赖它）——每次发版必须**人工补齐 config.yaml**。
> 2. **MiniMax-H3-lite**：`backend/main.py` 的 FastAPI `version` 与 `package.json` 是两套独立声明，无门禁，漏改时 `/api/health` 上报的版本会与项目版本不符。

## 3. 发版 Checklist（跨仓通用）

对任意一个仓库发版，按此顺序自检：

1. 【定版本】确认语义化版本号（遵循各仓 Conventional Commits 规则）。
2. 【改载体】按上表把该仓所有 `◆ 需人工同步` 的载体一次性改齐：

   - DraftPeek：跑 `./gradlew bumpVersion -Pbump=minor|patch`（自动写 gradle.properties，勿手改）。

   - Image：改 `config.yaml → version`。

   - MiniMax：改 `backend/main.py` 的 `version=` **和** `package.json` 的 `version`。

   - SeedVR2：改 `pyproject.toml → version`，运行 `pytest tests/test_version.py` 通过。

   - TTS：`pyproject.toml → version`（release-please 会改），**务必再补** `config.yaml → version`。

   - SpiritPal：`package.json` + `Cargo.toml[package].version` + `tauri.conf.json.version` 三处同时改，PR 过 CI 的 `check-version-consistency.js`。
3. 【同步 CHANGELOG】各仓更新 `CHANGELOG.md` 顶部标题（`## [x.y.z] - 日期`）。
4. 【打 tag】`git tag -a vX.Y.Z -m "Release vX.Y.Z"`，tag 与版本号严格一致（DraftPeek/SpiritPal 显式要求 `v` 前缀）。
5. 【触发 CI/发布】推送触发各仓 CI；带发布流水线的（SeedVR2 tag 便携包、TTS release-please、SpiritPal release.yml）盯到终态。

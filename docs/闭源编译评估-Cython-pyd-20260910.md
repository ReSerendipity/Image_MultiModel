# 闭源编译评估：Cython .pyd 方案（P2，2026-09-10）

> 任务书 P2 要求对「代码闭源」方向做评估并出具文档（含公开声明）。
> 本文档为**评估结论**，不改变当前开源现状；任何闭源改造须另行立项并经用户确认。

## 1. 结论（TL;DR）

**不建议在现阶段对 Image MultiModel 做 Cython/.pyd 闭源编译。** 收益有限、代价高、与
当前开源发布模式冲突；若未来确有闭源诉求，优先评估「分卷加密 + 授权校验」而非源码混淆。

## 2. 现状与诉求

- 当前：Apache-2.0 开源仓库，`app/integrated_app/` 纯 Python 源码随发布分发。
- 诉求假设：防止分发物中的 Python 源码被直接阅读/复制（商业保护）。

## 3. Cython 编译 .pyd 的技术评估

| 维度 | 评估 |
|---|---|
| 可行性 | 技术上可行：Cython 可将 `.py` 编译为 Windows `.pyd`（C 扩展），`pip install` 环节可替换 |
| 编译覆盖 | 33 个核心模块中约 60–70% 可编译；含动态特性（`eval`/`getattr` 字符串分发、模板、反射）的模块需改写 |
| 依赖冲击 | Comfy 内核/原生扩展/torch 动态图接口的模块编译后行为风险高（GIL、全局状态、反射） |
| 构建链 | 需 MSVC 工具链 + Cython + 按平台矩阵构建；CI 复杂度显著上升 |
| 调试成本 | 堆栈符号丢失、异常定位难；与现有 pytest 基线（1018 用例）对账成本高 |
| 兼容风险 | Python 3.12 小版本升级需重编译全部 .pyd（滚动维护负担）；第三方补丁难以协同 |
| 安全收益 | **有限**：.pyd 可逆向（反汇编/内存 dump）；Python 字节码与 .pyd 同被反编译只是难度略增 |
| 发布物影响 | 增量更新包体积变化小（.pyd 更小），但更新器/清单签名链路需适配新文件类型 |

## 4. 替代方案对比

| 方案 | 收益 | 代价 | 建议 |
|---|---|---|---|
| Cython .pyd | 源码不可直读 | 构建/维护/调试成本高，可逆 | 不推荐 |
| 模型权重加密（已有 `scripts/encrypt_weights.py` 思路） | 保护核心资产（模型） | 密钥管理复杂 | 按需评估 |
| 授权/订阅校验（服务端发证） | 商业化护栏 | 需在线/离线双模式设计 | 中期可评估 |
| 保持开源 + 社区/合规双赢 | 零成本、透明度高 | 无闭源保护 | **当前推荐** |

## 5. 公开声明

> **Image MultiModel 当前为 Apache-2.0 开源项目**，发布物中的 Python 源码以源码形式
> 随仓库与增量更新包分发，供社区审计与二次开发。项目未采用任何源码混淆或闭源编译，
> 亦无隐藏后门；完整性自检（清单签名 + enforce）保证发布物与仓库代码一致、可追溯。
> 若未来发布闭源商业版本，将另行公告并保留开源版本分支。

## 6. 若未来启动闭源改造的触发条件

1. 出现明确的商业授权/订阅收入模型且需要防护；
2. 核心模型资产（非源码）被批量盗用且造成实质损失；
3. 用户/客户明确提出闭源交付要求。

届时建议按「分卷加密 → 授权校验 → 局部 Cython（仅核心算法模块）」梯度推进，并在
发布流程（release_gate）中新增对应门禁。
